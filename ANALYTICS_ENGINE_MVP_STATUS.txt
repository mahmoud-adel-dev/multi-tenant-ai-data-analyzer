2. CURRENT ARCHITECTURE
-----------------------
Control plane (Next.js App Router, standalone build under PM2 as `aidl-web`):
  - Auth (next-auth) + org scoping; upload via Server Action or public REST
    (/api/v1/analyze with API-key bearer auth, idempotency keys).
  - MongoDB-backed job queue (`analysisjobs`) with atomic claim, heartbeats,
    stalled-job reclaim, capped retries; CONTRACT_VALIDATION_FAILED /
    MALFORMED_FILE are non-retryable by design.

Worker (`aidl-worker`, esbuild-bundled scripts/worker.ts):
  - Loads stored file -> POSTs to compute plane -> validates EVERY payload
    against AnalysisRunPayloadSchema (Zod) -> persists AnalysisRun +
    Dashboard + Report docs -> optional LLM narrative over VERIFIED data only
    -> notification. Structured JSON logs: ANALYSIS_STARTED,
    PARSING_COMPLETED, ANALYZING_COMPLETED, CONTRACT_VALIDATED /
    CONTRACT_VALIDATION_FAILED (issue count + first 5 paths),
    ANALYSIS_COMPLETED / ANALYSIS_FAILED with durationMs, rowCount,
    columnCount, RSS. Continuous 30 s heartbeat during long engine calls;
    max_memory_restart 1G safety net.

Compute plane (`aidl-analytics`, FastAPI + Polars/NumPy/SciPy/scikit-learn/
statsmodels, uvicorn :8000):
  - app/core/loader.py      CSV/TSV/XLSX/JSON loading w/ hard ceilings
  - app/profiling/flatten.py       recursive Struct -> dotted-path leaves
  - app/profiling/profiler.py      types, stats, quality findings, domain
  - app/profiling/semantics.py     path-token + value-pattern semantics
  - app/core/planner.py            AnalysisPlan BEFORE any metric runs
  - app/statistics/kpi.py          plan-driven KPIs + provenance
  - app/statistics/time_series.py  classification + partial-bucket guard
  - app/ml/outliers.py             method selection + business context
  - app/ml/segmentation.py         RFM / silhouette-guarded k-means
  - app/forecasting/engine.py      holdout vs naive baseline gating
  - app/visualization/planner.py   deterministic chart selection + insights
  - app/reporting/builder.py       dataset-aware executive report
  - app/schemas/contract.py        Pydantic contract (mirrors TS)

Contracts are mirrored in three places and kept in sync:
  analytics-service/app/schemas/contract.py
  src/lib/ai/analytics-schema.ts (Zod; boundary normalization for additive
                                  fields, strict element shapes elsewhere)
  src/types/analytics.ts

11. TREND ANALYSIS
------------------
State: MATHEMATICALLY CONSISTENT (the "stable (-56.4%)" class of contradiction
is impossible by construction).
Documented thresholds: |Δ|<5% stable; 5–25% moderate_growth/decline; >25%
strong_growth/decline; relative std >0.8 overrides endpoints → high_volatility;
<5 periods or zero variance → insufficient_data. directionLabel ALWAYS embeds
the measured change (e.g. "Strong Growth (+42.3%)"), so text can never disagree
with numbers; volatilityCoefficient persisted; seasonality via lag
autocorrelation with note; MA7/MA30 trailing windows materialized as arrays.
Insight text grounded in first/last/peak/trough values with explicit
non-causality hedging.

PARTIAL-BUCKET FIX (forecast visual drop): the trailing bucket whose date
coverage ends early (dataset ends mid-week/month) is EXCLUDED from the series
with lastPeriodComplete=false + engine warning — the artificial trough right
before a forecast is gone (verified: predictions start strictly after the last
complete history period).

Gaps: endpoint-based change% still noisy for long series (volatility flag
mitigates, doesn't replace); no STL decomposition; no YoY alignment.


12. ANOMALY DETECTION
---------------------
State: METHOD SELECTION + BUSINESS CONTEXT, VERIFIED.
Plan chooses methods by data shape: n≥500 & ≥3 clean measures → IQR +
robust z-score + Isolation Forest (2% contamination); n≥30 → univariate only;
else IQR alone. Every anomaly carries classification:
  * statistical_outlier — distributional flag, explanation explicitly states
    it does NOT indicate an error;
  * business_notable — statistically unusual but operationally plausible
    (positive extreme quantity = possible bulk order; positive revenue
    extremes = possible high-value orders; negatives in monetary fields are
    flagged as likely refunds/errors instead).
Dashboard widget shows split counts; severity from tail share.
Degenerate-spread case handled (constant column + one extreme is flagged).
Verified: classification enum populated on 100k run; method list respected.

Gaps: LOF implemented? No (documented option, not added — avoided extra dep);
time-series-specific anomaly methods (STL residuals) absent; per-column
business thresholds not user-configurable yet.


13. FORECASTING
---------------
State: BASELINE-ACCOUNTABLE AND SELF-WITHHOLDING.
Requirements: ≥12 complete periods, variance>0, chronological holdout (~20%)
where Holt damped-trend must beat BOTH MAPE≤60% AND a naive/seasonal-naive
baseline — otherwise the forecast is WITHHELD and the reason becomes an engine
warning (surfaced as "Completed with warnings"). fitMetrics={mape, mae,
baselineMape, skillScore}; validationMethod="chronological holdout vs naive
baseline". Uncertainty bands widen ∝√step using one-step-difference sigma
(convolution edge-artifact removed). Predictions continue from the last
COMPLETE period label in the identical format (continuity verified).
Verified on 100k: forecasts present with skillScore>0 (e.g. subtotal
MAPE 27.1 vs naive 44.3, skill 0.387).

Gaps: single model family (Holt); SARIMA/Holt-Winters seasonal fitting,
Prophet-style holiday effects, and per-method selection by seasonality
strength are future work; bands are Gaussian approximations.

19. SCALABILITY
---------------
Designed-for vs built-for:
  * Vectorized Polars throughout; O(n·cols) profiling; correlations capped
    (60 pairs); anomalies capped (300); series capped (400 pts); findings
    capped (150/200). No O(n²) on the critical path for the supported shape.
  * Single-node, single-process engine: datasets that exceed RAM (or the 250 MB
    upload ceiling) are out of scope TODAY. No chunked/streaming ingestion, no
    DuckDB/Parquet intermediate store, no partitioned execution, no horizontal
    worker pool (one worker process by design; queue supports more).
  * MongoDB: AnalysisRun stores FULL payload (incl. dashboard/report plans) in
    one document — fine at current sizes (~few MB) but approaching the 16 MB
    doc limit is plausible for very wide schemas; splitting plans into their
    collections is recommended before 500k+ rows become common.
Verdict: reliable to low hundreds of thousands of rows on commodity hardware;
beyond that needs the streaming/store work itemized in section 28.

---------------------

   descriptions, insight sentences) is English-only; see §17.

   answering, and the improved flow was not exercised against a live model

   or exploded dimensions).

8. Ingestion is in-memory end-to-end; 250 MB / 5M-row ceilings are hard walls
   rather than streaming boundaries.

10. First-paint locale flash possible (server renders LTR default; client
    applies stored AR cookie post-hydration).
